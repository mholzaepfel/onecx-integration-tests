= Platform Configuration Contract (`platform.json`)

The runner derives all startup behavior from a single JSON file, `platform.json`. This page describes every supported field, its type, accepted values, and how validation is enforced. Validation uses AJV at startup and fails immediately on any missing or invalid value, so configuration errors are reported before any container is started.

== Overview

The runtime contract is defined by `platform.json` and validated against `integration-tests.schema.json`.

Validation behavior:

* Validate JSON syntax
* Validate schema constraints with AJV
* Fail fast when required fields are missing or invalid
* Search default path first, then fallback to recursive discovery

Default lookup order:

* `integration-tests/platform/platform.json`
* First file matching `*platform.json` under the current working directory

The expected top-level format is:

[source,json]
----
{
	"platformConfig": {
		"importData": true,
		"withLoggingEnabled": true,
		"heartbeat": { "enabled": true }
	}
}
----

== Platform Config

[.stripes-even,cols="25,20,55"]
|===
| Field | Type | Description

| `importData`
| `boolean`
| Run default data import after platform startup

| `withLoggingEnabled`
| `boolean` or `string[]`
| Enable logging for all containers or only selected container names

| `heartbeat`
| `HeartbeatConfig`
| Configure continuous health checks with `enabled`, `interval`, and `failureThreshold`

| `platformOverrides`
| `object`
| Override image tags for core, services, BFF, and UI containers

| `container`
| `object`
| Define user-managed service, BFF, UI, and E2E containers
|===

Example with heartbeat and E2E:

[source,json]
----
{
	"platformConfig": {
		"importData": true,
		"withLoggingEnabled": true,
		"heartbeat": {
			"enabled": true,
			"interval": 10000,
			"failureThreshold": 3
		},
		"container": {
			"e2e": [
				{
					"image": "e2e-example:latest",
					"networkAlias": "e2e-example"
				}
			]
		}
	}
}
----

=== Platform Overrides

Use `platformOverrides` to test specific image versions.

[source,json]
----
{
	"platformConfig": {
		"platformOverrides": {
			"core": {
				"keycloak": { "image": "quay.io/keycloak/keycloak:23.0.4" }
			},
			"services": {
				"tenant": { "image": "ghcr.io/onecx/onecx-tenant-svc:main-native" }
			},
			"bff": {
				"shell": { "image": "ghcr.io/onecx/onecx-shell-bff:main-native" }
			},
			"ui": {
				"shell": {
					"image": "ghcr.io/onecx/onecx-shell-ui:main",
					"remoteEntry": "/onecx-shell/mf-manifest.json",
					"remoteBaseUrl": "/onecx-shell/"
				}
			}
		}
	}
}
----

Apply release semantics consistently:

* `main` for latest main-branch build images

For the predefined Shell and Workspace UIs, use `platformOverrides.ui.<name>.remoteEntry` and `remoteBaseUrl` to override either path independently. The runner resolves relative paths against the predefined container's network alias and internal port.

[IMPORTANT]
====
The runner does not detect whether an image serves `remoteEntry.js` or `mf-manifest.json`. The bundled import files reference `remoteEntry.js`. When switching to an image that serves `mf-manifest.json`, such as Shell v3 or an Angular 21 application, also set `remoteEntry`, for example `/onecx-shell/mf-manifest.json`.
====

== Container Definition

User-defined containers are configured under `platformConfig.container`.

=== Service Container

Required fields:

* `image`
* `networkAlias`
* `svcDetails.databaseUsername`
* `svcDetails.databasePassword`

Optional fields:

* `environments`
* `healthCheck`

=== BFF Container

Required fields:

* `image`
* `networkAlias`
* `bffDetails.permissionsProductName`

Optional fields:

* `environments`
* `healthCheck`

=== UI Container

Required fields:

* `image`
* `networkAlias`
* `uiDetails.appBaseHref`
* `uiDetails.appId`
* `uiDetails.productName`

Optional fields:

* `environments`
* `uiDetails.remoteEntry`: relative path or absolute HTTP(S) URL of the Module Federation entry file
* `uiDetails.remoteBaseUrl`: relative path or absolute HTTP(S) URL used as the remote application base

Configure both locations independently. For example, an entry file can be nested while the application base remains at the container root.

[source,json]
----
{
	"platformConfig": {
		"container": {
			"ui": [
				{
					"image": "ghcr.io/onecx/onecx-workspace-ui:main",
					"networkAlias": "onecx-workspace-ui",
					"uiDetails": {
						"appBaseHref": "/mfe/workspace/",
						"appId": "onecx-workspace-ui",
						"productName": "onecx-workspace",
						"remoteEntry": "/manifests/mf-manifest.json",
						"remoteBaseUrl": "/workspace/"
					}
				}
			]
		}
	}
}
----

Choose how to provide the entry location:

* Prefer `uiDetails` for user-defined UIs and `platformOverrides.ui.<name>` for predefined Shell and Workspace UIs. This keeps import files independent of container aliases and ports.
* Omit a setting to use the corresponding relative or absolute value from the microfrontend import file.
* If neither configuration nor import data provides a value, use `/remoteEntry.js` for the entry and `/` for the application base.

During product-store import, the runner:

* Matches `uiDetails.appId` to the application ID in each microfrontend import filename.
* Builds the host from the UI container's `networkAlias` and internal port.
* Selects `remoteEntry` and `remoteBaseUrl` independently from UI configuration, import data, or the defaults, in that order.
* Resolves relative selected values against the UI container host and keeps absolute HTTP(S) values unchanged.

With alias `workspace-ui` and port `4200`, the example resolves to `http://workspace-ui:4200/manifests/mf-manifest.json` and `http://workspace-ui:4200/workspace/`.

== E2E Container

The E2E container list is optional and runs after platform startup and health checks.

Execution behavior:

* `container.e2e` is an array.
* Entries are executed sequentially in array order.
* Each entry must have a unique `networkAlias`.

Required fields:

* `image`
* `networkAlias`

Optional fields:

* `baseUrl`

Example:

[source,json]
----
{
	"platformConfig": {
		"container": {
			"e2e": [
				{
					"image": "ghcr.io/onecx/onecx-shell-e2e:latest",
					"networkAlias": "shell-e2e",
					"baseUrl": "http://onecx-shell-ui:8080"
				}
			]
		}
	}
}
----

[IMPORTANT]
====
The E2E container runs as a one-shot test workload and is expected to terminate with an explicit exit code
====
